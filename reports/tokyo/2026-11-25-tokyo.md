## 3. T2: batch shadow evaluator (the shadow of record)

**Code.** `lp_arb/shadow_eval.py` (one completed UTC day), `lp_arb/shadow_report.py` (cumulative table, pass/kill), `lp_arb/fees.py`, units `deploy/lp-arb-shadow.service` + `.timer`. No rule logic is re-implemented: per window it calls the frozen `market_metrics` (vendored byte-identical copy of `~/lighter-shadow` @1348b2e in `lp_arb/frozen_code/`, git blob hashes checked at every start) and `overnight/t1_arb.ext`. New code is only loading, the fee lookup, recorder-health counters, and a per-trigger persistence walk that follows the same trigger sequence as `ext()` and asserts the same trigger count per window.

**Frozen before any shadow data existed:** `frozen/t1_shadow_eval_spec.json`, commit 4eb810a (21:41 UTC 11-24). It pins what the candidate file left open:
- count starts 2026-11-25 00:00 UTC; a BTC day counts if ≥ 90% of its windows have a valid two-venue book on ≥ 50% of the grid; the first 14 such days count;
- clock = this box's receive times for both venues (as in the holdout; the candidate file's "Polymarket book from Dublin" is dropped, see `docs/box-tokyo.md` §5);
- pessimistic count = 500+500 fills whose Lighter quote and PM hedge each still show ≥ 5 shares at the price 100 ms after their match;
- **+300 ms persistence for pass/kill = share of Lighter-leg fills whose trigger quote is still displayed 300 ms after the trigger** — the measure that gave 0.918 on the holdout and against which 0.80 / 0.65 were set. The share over *all* triggers is reported next to it, descriptive only;
- settlement map Lighter outcome 2 = Up, 1 = Down (holdout 1,099 + 998 = 2,097/2,097);
- fee/resolution change = Gamma `feeType`/rate or resolution-text hash differs from the first counted day.

**The persistence finding (important for reading the shadow).** On the holdout, per trigger, the Lighter quote is still displayed at +100 ms 0.78, **+300 ms 0.66**, +500 ms 0.60 (BTC, 2,438 triggers; ETH 0.76 / 0.61 / 0.53). The 0.91 in the registered report is conditional on the quote being there at +500 ms (the fill), so it mostly measures flicker inside fills, not how often someone takes the quote first. The frozen pass/kill uses the conditional measure (spec above). Read per trigger, the holdout would sit right at the 0.65 kill line and fail the 0.80 pass. The fill rate itself (60%) is already inside the backtest's P&L, so this does not change the money numbers; it does mean "persistence ≥ 0.80" is a weaker check than its wording suggests.

**Recorder health on the holdout days (BTC 15m, from the same run):** PM disconnect rows 2–8 per day (72 on 11-13); minutes whose `last_err` is a 1013 close 5–51 per day (a lower bound: the journal keeps the last error per minute); **4–15% of PM rows > 1 s late** per day; Lighter book-unknown rows 9–364 per day. "Gaps > 5 s" (200–500 PM, 800–1,300 Lighter per day) count quiet books as well as outages, so they are context, not failures. The PM lateness means the backtest's PM price is sometimes seconds stale. The holdout had the same lateness, so the shadow is comparable, but a live hedge would see a fresher book.

**Daily run.** `lp-arb-shadow.timer` at 00:50 UTC runs `shadow_eval.py --pending` (every completed day from 11-25 not yet in `days.csv`, oldest first, max 3, so `Persistent=true` after downtime does not skip days), then `paper_vs_shadow.py --yesterday`, then `shadow_report.py`. With no counted day, the report prints `WAITING`. After installation, the first counted day is 11-25, evaluated on 11-26 00:50.
